# Classic Asset Descriptor and XDR Codec

## What this does
The Classic Asset Descriptor and XDR Codec is an offline developer workbench that converts Stellar classic asset identities between canonical text descriptors, structured JSON models, and base64-encoded Asset XDR. It operates bidirectionally: developers can encode classic descriptors (such as `native` or `USDC:G...`) into standard base64 XDR payloads, or decode base64 Asset XDR payloads back into canonical descriptors and structured metadata without making external RPC or network requests.

## How it works
The slice pipeline processes inputs through three explicit stages:
1. **Validation & Normalization (`schema.ts`)**: Accepts raw user strings or typed objects specifying an operation mode (`encode` or `decode`). It enforces character and length bounds (`MAX_INPUT_LENGTH`), validates base64 structure for XDR, verifies Stellar asset code constraints (1-12 alphanumeric characters), validates Ed25519 public key checksums via `StrKey.isValidEd25519PublicKey`, and strictly rejects secret seeds starting with `S`.
2. **Domain Transformation (`lib/assetDescriptorCodec.ts`)**:
   - In `encode` mode, native representations (`native` or `XLM`) map directly to `Asset.native()` (`AAAAAA==`). Issued assets are segmented into code and issuer, categorized across the `credit_alphanum4` (1-4 characters) and `credit_alphanum12` (5-12 characters) boundary, and serialized to base64 XDR via `asset.toXDRObject().toXDR("base64")`.
   - In `decode` mode, base64 payloads are verified for valid length and root discriminant bounds (0 to 2). The decoder parses the payload via `xdr.Asset.fromXDR()`, verifying that the buffer is completely consumed (rejecting trailing bytes) and that unsupported variants like liquidity pool shares (discriminant 3) produce explicit `unsupported_asset_type` errors.
3. **Reactive Presentation (`components/`, `hooks/`)**: The `useAssetDescriptorCodec` hook manages a four-state machine (`idle`, `loading`, `success`, `error`) with request deduplication to prevent race conditions. Results render canonical values, codes, issuers, types, and XDR with dedicated copy controls and a reset action.

## Why it is built this way
- **Distinguishing Native XLM from Issued XLM**: In Stellar, native XLM has no issuer and serializes to discriminant 0 (`AssetType.assetTypeNative`), whereas an issuer can legitimately issue a credit asset with the code `XLM` (discriminant 1, `AssetType.assetTypeCreditAlphanum4`). Many naive implementations mistakenly collapse any asset with code `XLM` into `Asset.native()`, or conversely populate a dummy/guessed issuer for native assets. This codec strictly enforces `native` as the canonical descriptor for native XLM and preserves the issuer for credit assets named `XLM` (`XLM:G...`), ensuring reversible, collision-free round trips.
- **Root Discriminant Isolation & Buffer Exhaustion**: Horizon endpoints and Soroban contracts often interchange standard assets and liquidity pool shares or `ChangeTrustAsset` unions. Attempting to parse non-standard discriminants through generic decoders risks misclassifying pool share identifiers or ignoring trailing garbage bytes appended to base64 payloads. The decoder inspects the 32-bit big-endian union discriminant prior to deserialization and asserts complete buffer consumption, guaranteeing that invalid or trailing bytes trigger `invalid_input` and pool shares trigger `unsupported_asset_type` rather than silent corruption.
